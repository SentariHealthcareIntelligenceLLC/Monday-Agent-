## 5. Decisions carried forward — do not relitigate

- **Six hourly crons + local-hour matching is deliberate** (Vercel cron is UTC-only; this is DST-proof). Don't convert to fixed UTC hours. The single-`/api/cron/tick` consolidation in CONFIG_OPTIMIZATION.md is optional and needs a small code change.
- **RLS with no anon policy is intentional**; 0002 adds *authenticated* policies only. The `rls_enabled_no_policy` advisories on tables without policies are expected.
- **Every view stays `security_invoker = true`** — all new views comply; any future view must too.
- **Raw Meta tokens never go in tables** — Vault names only (`whatsapp_accounts.*_secret_name`).
- Reports tab stays showing "no case-log source connected" until a real feed exists.
- The dashboard's CSS/markup is the user's approved design — extend the adapter, don't restyle. The demo reuses its tokens for that reason.
- **PHI**: WhatsApp Cloud API is not HIPAA-eligible; no patient identifiers in task titles/notes; photo proof only in the private bucket.

## 6. Code changes these migrations enable (not yet written)

The migrations are live-safe on their own — the Node service (service_role) bypasses
RLS and keeps working unchanged. To *use* the new capability:

1. **Dashboard login**: swap Basic auth for Supabase Auth (`@supabase/supabase-js`,
   `signInWithOtp`), send the session JWT to the API; keep `ADMIN_PASSWORD` as a
   break-glass fallback. `profiles.app_role` drives what each tab shows.
2. **WhatsApp service**: read sender config from `whatsapp_accounts` (resolve Vault
   names server-side) instead of env vars; write webhook payloads to
   `whatsapp_webhook_events`; insert `whatsapp_delivery_status` rows from Meta
   status callbacks; consult `v_wa_session_open` to pick template vs free-form.
3. **Connections tab**: surface `whatsapp_accounts` + `whatsapp_contacts`
   (opt-in state, last inbound, failures) in the dashboard.
